# ShortLink 短链接系统 · 简历项目面试手册

> 本手册对应简历上这 6 个要点。每一节的结构是：**先给一段可直接背的口述稿**，然后**扮演大厂面试官**，列出面试官顺着这一点最可能追问的问题，并给出标准答案。开头先放一段最关键的"工作流程解读"——面试时被问"讲讲你这个项目是干嘛的"，先把这段故事讲清楚，再往下钻技术方案，会自然得多。

## 📌 简历要点（骨架）

> - **异步消息入库**：使用 Redis Stream 消息队列实现访问监控数据异步入库，采用消费者组模式 + 手动 ACK 机制；使用 Redis 幂等标记并通过数据库唯一索引兜底实现消息仅消费一次，配合定时任务巡检 Pending 列表恢复超时消息，保障消息可靠性
> - **分布式号段生成**：短链接创建时，通过 Redis 的 INCRBY 实现分布式号段分发，减少对 Redis 的请求；本地原子自增 id 并异步预取下一号段；Base62 编码缩短码长度，仿射置换打散连续序号使其不可预测
> - **多级缓存防护**：跳转链路采用 Caffeine 本地缓存 + Redis 分布式缓存 + 布隆过滤器 + 空值缓存的四层防御；通过布隆过滤器拦截非法短码，使用本地 ReentrantLock + 双重检查防止缓存击穿，避免分布式锁的尾延迟放大
> - **双层接口限流**：基于 Guava RateLimiter 令牌桶算法实现接口级限流（创建/跳转/统计分类配置）；基于 Redis + Lua 滑动窗口实现用户级分布式限流，防止恶意高频调用
> - **HyperLogLog 去重统计**：使用 Redis HyperLogLog 替代 Set 进行 UV/UIP 去重，以固定 12KB 内存统计海量去重计数；通过 Lua 脚本原子计算增量并写入数据库聚合表；采用奇偶日轮转 key 实现日活自动重置
> - **MCP 工具接入**：基于 MCP（Model Context Protocol）协议对外暴露短链接创建工具，使用 SSE 传输，支持 AI 智能体直接调用

## 🔑 最关键的解读：这个短链接系统到底在干嘛（业务与用户视角）

> ⚠️ **这一段是最重要的。** 面试官问"介绍下你的项目"，80% 的人会背技术栈，但讲不清楚业务。你只要能用人话把下面这套流程讲明白，就已经超过一大半候选人了。先把业务讲透，再往下钻技术，节奏会很顺。

### 一句话理解

> 短链接系统干的就是一件事：**你给我一个又臭又长的网址，我吐给你一个短小精悍的短网址；别人点这个短网址，我帮他一秒钟跳回原来的长网址；同时我偷偷帮你记下来——谁点的、什么时候点的、用什么手机点的、从哪个城市点的**。所以它其实是三个产品合一：**一个"翻译机"（长短互转）、一个"导航台"（点击跳转）、一个"侦察兵"（访问追踪）**。

### 为什么用户需要它（业务驱动力）

> 在讲流程前先想清楚：谁会用这玩意儿，为什么要用？面试官经常问"你这个项目解决什么问题"。
>
> 1. **链接太长，发不出去**：营销短信按字数收费，一个长 URL 可能多花好几毛钱；微博有字数限制；微信群里长链接被折叠得很难看。短链接能省成本、省版面。
> 2. **要追踪效果**：运营人员在 10 个渠道（公众号、抖音、小红书、短信…）投了同一个落地页，怎么知道哪个渠道效果好？给每个渠道生成一个独立的短链接，后台就能看到每个渠道的点击量、地域分布、设备分布——这就是"投放归因"。
> 3. **链接要能管理**：活动结束想下线某个链接、想批量改跳转地址、想设置过期时间——长链接做不到，短链接系统是一个"链接的中台"，统一管理。
> 4. **防封防刷**：有些平台会屏蔽特定域名，短链接可以换一个"门面域名"绕过；同时系统可以做风控，拦住恶意点击。
>
> 所以这个系统的核心价值不是"短"，而是 **"短 + 可跳转 + 可追踪 + 可管理"** 这一套组合拳。市面上 bit.ly、腾讯短网址、新浪短网址都是这个生意。

### 流程一：用户注册和登录（拿到"通行证"）

> 小明打开网站，首页有个输入框——**不登录也能用**，直接把长链接粘进去就能转成短链接（这是"公开创建"功能，给临时用户用的，归到一个公共账户下）。但小明想管理自己的链接、看统计数据，于是点了"注册"。
>
> 注册时填用户名、密码、手机号、邮箱。系统做了两件事：
> 1. **创建账户**：密码用 BCrypt 加密存储（不是明文，也不是 MD5——BCrypt 每次加密结果都不同，靠盐值防彩虹表），手机号和邮箱用 AES 对称加密（因为这些字段需要反查明文，不能用不可逆的哈希）。
> 2. **送一个"默认分组"**：自动给小明建一个叫"默认分组"的文件夹，以后他创建的短链接默认放这里——就像浏览器书签的默认收藏夹。
>
> 登录成功后，系统发给小明一张"通行证"（Token），后续每个操作都要带着它，系统才知道"现在操作的是小明"。通行证有有效期，每次操作自动续期，长时间不操作就失效，要重新登录。

### 流程二：创建一个短链接（"翻译机"工作）

> 小明登录后在后台点"创建短链接"，填入一个 B 站视频链接 `https://www.bilibili.com/video/BV1xx411c7mD`，选分组、写描述"面试资料"，点提交。系统背后干这几件事：
>
> **第 1 步：生成短码（取号 + 打乱 + 编码）。**
> 系统内部有一台"取号机"。每次创建短链接，取号机吐出一个全局唯一的递增编号（比如第 10086 号）。但这个编号不能直接当短码——一来连续的号容易被猜出来（看到 `10086` 就猜下一个是 `10087`，有安全风险），二来数字太长。所以做两道处理：
> - **仿射置换**：用一个数学公式 `y = (A × 编号 + B) mod N` 把编号"打乱"成看似随机的数，比如 10086 可能被打散成 38472910。A 和 B 是启动时随机生成的，外人猜不到。这个变换是可逆的——给定短码能反算出编号，这个能力后面跳转时有大用。
> - **Base62 编码**：把这个数用 `0-9 A-Z a-z` 共 62 个字符编码，6 位就能表示 568 亿个数，足够用十几年。最终得到一个 6 位短码，比如 `Ab3xK9`。拼上域名就是 `http://s.link/Ab3xK9`。
>
> 这台取号机不是每次都现取——那样 Redis 压力太大。而是**一次取一整段号**（默认 1 万个连续编号）存到本地内存，之后每次创建短链接直接在本地自增。快用完了再异步去 Redis 取下一段。
>
> **第 2 步：存进数据库（而且要分库分表）。**
> 短链接数据会越攒越多，单表迟早扛不住。所以用 ShardingSphere 按"分组 ID（gid）"做哈希分片，分成 16 张表（`t_link_0` ~ `t_link_15`）。小明这次创建的链接属于分组 A，哈希后可能落到第 7 张表。
>
> 这里有个巧妙设计：**存两张表**。一张是主表 `t_link_N`，存短链接的完整信息（原始地址、分组、有效期、创建时间…）；另一张是路由表 `t_link_goto_N`，只存"短地址 → 分组 ID"的映射。为什么？因为跳转时我们手里只有短地址，不知道它属于哪个分组，而主表是按 gid 分片的——没有 gid 就不知道去哪张表查。所以先用路由表查到 gid，再去对应分片查详情。路由表是按短地址分片的，保证跳转时一次就能查到 gid。
>
> **第 3 步：预热缓存。**
> 创建完立刻把"短地址 → 原始地址"写进 Redis 缓存，并登记进布隆过滤器（一个记录"所有被创建过的短链接"的高效集合）。这样**别人第一次点这个短链时，直接命中缓存，不用查数据库**。
>
> **第 4 步：返回结果。**
> 小明拿到 `http://s.link/Ab3xK9`，复制走，爱发哪发哪。

### 流程三：别人点击短链接（"导航台"+"侦察兵"同时工作）⭐核心

> 这是整个系统**流量最大、最考验性能**的环节。小红在群里看到 `http://s.link/Ab3xK9`，点了一下。她的浏览器向系统发请求："我要访问 /Ab3xK9"。系统要在**几毫秒内**完成跳转，让小红感觉"一点就过去了"。同时还要偷偷记下这次访问。整个流程分两条线并行：
>
> #### 🅰️ 主线：找到原始地址并跳转（四层缓存漏斗）
>
> 系统从最快到最慢，一层层找原始地址：
>
> **第 1 层 · 本地小本本（Caffeine 本地缓存）。** 系统先在自己进程内存里翻——这个短地址最近有人点过吗？点过的话原始地址就记在小本本上了。命中就直接跳，全程不到 1 毫秒，连网络都不用走。热点短链接（比如大 V 发的）99% 走这一层。
>
> **第 2 层 · 共享大仓库（Redis 分布式缓存）。** 小本本没有？去 Redis 这个"所有实例共享的大仓库"找。找到了就顺手抄一份回小本本（下次就快了），然后跳转。
>
> **第 3 层 · 存在性防护。** 如果 Redis 也没有，先别急着查数据库——可能是有人拿随机短码在乱试：
> - **布隆过滤器**：查一下"所有创建过的短链接"集合里有没有它。没有就直接 404。布隆过滤器有个特点——说"没有"就一定没有（不会漏判），说"有"可能误判（99.9% 准确）。
> - **空值缓存**：之前有人查过这个短码、数据库里确认没有，就在 Redis 里记了个"这玩意不存在"的标记，30 分钟有效。30 分钟内再有人查同一个短码，直接 404，不用再查库。这是防"缓存穿透"（有人拿不存在的短码狂刷数据库）。
>
> **第 4 层 · 查数据库（极少数情况才走到这）。** 四层都没拦住，说明要么是真存在但缓存刚好失效了，要么是真不存在但布隆过滤器误判了。这时要查数据库，但有个风险——**缓存击穿**：如果恰好一个热门短链接缓存刚过期，一瞬间几万个请求同时涌向数据库，数据库会被打挂。所以这里加了一把**本地锁**：同一个短地址，同一时刻只让一个请求去查数据库，其他请求排队等。拿到锁的请求查完数据库、把结果填回缓存后，排队的请求醒来发现缓存已经有了，直接用。为什么用本地锁不用分布式锁？因为分布式锁每次要跑两趟 Redis（加锁、解锁），在高并发下会把延迟放大好几倍；本地锁是纯内存的，快得多。代价是多个服务器实例可能各自查一次数据库——但查询是幂等的，多查一次无伤大雅，换来的是确定性的低延迟，值。
>
> 查到原始地址后，系统返回一个 **302 重定向**（告诉浏览器"你要的东西在 bilibili 那个地址，自己跳过去"），小红的浏览器就自动跳转了。
>
> #### 🅱️ 副线：偷偷记一笔访问数据（侦察兵）
>
> **关键点：统计是异步的，绝不拖慢跳转。** 跳转的同时，系统把这次访问的关键信息（谁点的、什么 IP、什么浏览器、什么系统、什么时间）打包成一条消息，**扔进 Redis Stream 消息队列**，然后立刻完成跳转返回。小红的感觉就是"瞬间跳转"，完全不知道背后还记了账。
>
> 后台有一群"记账员"（消费者）在慢慢处理这些消息：把每条访问拆解到不同的统计维度表里——今天 PV 加 1、如果是新访客 UV 加 1、IP 归属地是杭州就给浙江计数加 1、用的是 iPhone 就给 iOS 计数加 1……这些写入是慢慢来的，跟跳转完全解耦。
>
> 万一某个记账员写到一半挂了呢？消息会不会丢、会不会重复？这就是"消息可靠性"要解决的问题——后面第一点会详细讲。

### 流程四：查看统计数据（"侦察兵"的战报）

> 第二天，小明想看自己链接的战绩，打开后台"数据分析"页。他能看到：
>
> - **基础数据**：总浏览量 PV、独立访客 UV、独立 IP 数 UIP——今天多少、累计多少。
> - **时间趋势**：每天/每小时/每星期的折线图，看出哪个时段最活跃。
> - **地域分布**：访问者来自哪些省市（靠 IP 地址反查地理位置）。
> - **设备画像**：Chrome/Safari/微信内置浏览器占比；iOS/Android/Windows 占比；手机/电脑/平板占比；WiFi/4G/5G 占比。
> - **访客类型**：新访客 vs 老访客比例（靠"首访记录表"判断）。
> - **高频 IP 排行**：哪些 IP 点得最频繁（也能用来识别刷量）。
>
> 这里的技术难点是 **UV/UIP 去重**。PV 好算，点一次加一次。但"独立访客"——同一个人点 100 次也只能算 1 个 UV。如果用集合（Set）把每个访客的标识都存下来，内存会爆。所以用 **HyperLogLog** 这个概率数据结构，固定 12KB 内存就能统计几十亿去重数，误差只有 0.81%，对运营分析完全够用。具体怎么算出"这次点击是不是新访客"、怎么做到按天重置，后面第五点会讲。

### 流程五：管理链接（"中台"能力）

> 小明用久了，链接越来越多。他可以：
> - **分组管理**：建"面试资料""技术文章""个人项目"等分组，拖拽排序，链接可在分组间移动。
> - **编辑**：改目标地址、描述、有效期。改完缓存自动失效更新。
> - **回收站**：不要的链接先软删除（移进回收站），后悔了能恢复；确认不要了再永久删除。软删除的好处是可恢复，而且保留了"链接曾经存在过"的痕迹（统计不丢）。
> - **API Token**：小明是开发者，想在程序里自动创建短链，就生成一个 API Token，用 REST API 调用。Token 和登录通行证是两套独立凭证，适合程序化使用。

### 流程六：AI 助手也能创建短链（开放能力）

> 系统还开了个"对外开放窗口"——MCP（Model Context Protocol）接口。支持 MCP 协议的 AI 助手（比如 Claude）可以直接调用系统创建短链。场景：小明跟 AI 说"帮我把这个链接缩短一下"，AI 自动调用 MCP 工具，返回短链给小明。等于把短链接能力变成 AI 生态里的一块"乐高积木"，任何 AI 应用都能拼上去。

### 把六条流程串成一张全景图

> ```
> 注册/登录 ──→ 拿到通行证(Token)
>     │
>     ▼
> 创建短链 ──→ 取号机取号 ──→ 仿射打乱 ──→ Base62编码 ──→ 6位短码
>     │         (一次取1万个,   (y=(Ai+B)%N)     (0-9A-Za-z)
>     │          本地自增)
>     ▼
> 存数据库(按gid分16表) + 预热Redis缓存 + 登记布隆过滤器
>     │
>     ▼
> 返回 http://s.link/Ab3xK9  ──→ 小明拿去分享
>     │
>     ▼
> 别人点击 ──→ 四层缓存漏斗找原始地址 ──→ 302跳转
>            (Caffeine→Redis→布隆/空值缓存→DB+本地锁)
>     │
>     └──同时──→ 扔进Redis Stream队列 ──→ 后台消费者慢慢记账
>                                        (PV/UV/地域/设备/浏览器...)
>     │
>     ▼
> 小明看统计后台 ◄─── 消费者把数据落库后的聚合结果
> ```
>
> **核心价值三件事**：生成短码（快、唯一、不可预测）、跳转（毫秒级、扛高并发）、统计（异步不拖慢跳转、多维分析）。围绕这三件事，加上用户/分组/回收站/Token/MCP，就是一个完整产品。

## 一、异步消息入库 — Redis Stream 消费者组 + 手动 ACK + 三层幂等

### 📝 口述稿

> 短链接跳转是系统流量最大的路径，每次跳转都会产生一条访问记录（UV 标识、IP、浏览器、操作系统、设备、网络等）。如果在跳转的热路径上同步写数据库，每次跳转都要等 DB 写完才能返回 302，响应时间会被严重拖长，而且高并发下数据库连接池很快就会被打满。
>
> 所以我用 **Redis Stream** 做了一层异步解耦。具体流程：跳转完成后，通过 `XADD` 把这条访问事件写成一条消息扔进 Stream，然后**立即返回 302 重定向**，整个过程控制在毫秒级，用户完全感觉不到背后有统计在发生。
>
> 消费端我用了 Redis Stream 的 **消费者组（Consumer Group）模式**。启动时通过 `XGROUP CREATE` 创建消费者组，多个消费者实例订阅同一个 Stream Topic，Redis 会自动把消息负载均衡到不同消费者，每条消息只被组内一个消费者处理。每个消费者通过 `XREADGROUP` 阻塞拉取消息，每次最多拉一批，处理完用 `XACK` 手动确认。
>
> 最关键的是**消息可靠性**。我采用了 at-least-once（至少投递一次）+ 幂等消费的组合，设计了**三层防护**保证消息不丢、不重：
>
> **第一层 · Redis 幂等标记。** 消费前先用 `SETNX`（setIfAbsent）抢一个标记，值为 "0" 表示"处理中"，TTL 2 分钟。如果抢不到说明别的消费者正在处理或已处理过，直接跳过。消费成功后把标记值改成 "1"，TTL 延长到 4 分钟。
>
> **第二层 · 数据库唯一索引兜底。** 访问日志表上有 `message_id` 的唯一索引。就算幂等标记失效导致重复消费冲进来了，数据库也会因为唯一约束抛 `DuplicateKeyException`，我在 catch 块里把它当成"已处理成功"直接吞掉。
>
> **第三层 · 定时任务巡检 PEL。** 消费者如果崩溃了，它领走但没 ACK 的消息会留在 PEL（Pending Entries List）里。我写了个定时任务，每 30 秒用 `XAUTOCLAIM` 命令，认领那些"空闲超过 2 分钟还没 ACK"的消息，交给一个叫 `stats-recoverer` 的恢复消费者重新处理。巡检用 Lua 脚本保证原子性，游标持久化在 Redis 里，应用重启也不丢进度。
>
> 这样一套下来，消息不会丢（PEL + 巡检兜底），也不会重复写入（幂等标记 + 唯一索引双保险）。

### ❓ 面试官追问

#### Q1：为什么选 Redis Stream 而不是 Kafka 或 RabbitMQ？

> **A：** 主要是两个考虑。
>
> 第一，**技术栈精简**。项目本身已经重度依赖 Redis 做缓存、分布式锁、号段分配、限流，再引入 Stream 不需要额外部署 MQ 中间件。我的部署是 Docker Compose 三个容器（应用 + MySQL + Redis）就跑起来了，运维成本极低。引入 Kafka 要额外搭 ZooKeeper/KRaft、Broker，对一个短链系统这个量级是过度设计。
>
> 第二，**语义匹配**。Redis Stream 原生支持 Consumer Group、手动 ACK、PEL（Pending Entries List）这些特性，能直接满足 at-least-once 的消费语义，和 RabbitMQ 的 ack 机制语义一致。访问统计这个场景是典型的"最终一致性"需求——允许几秒延迟，对吞吐要求是单机几千 QPS，Redis Stream 完全够用。
>
> 如果未来日访问量涨到千万级、需要严格的顺序消费和更高的吞吐，会考虑迁移到 Kafka。Kafka 在分区并行消费、持久化可靠性、 Exactly-Once 语义上更强，但当前场景下 Redis Stream 是更轻量的选择。

#### Q2：消费者挂了，消息会丢吗？具体怎么恢复？

> **A：** 不会丢，这正是消费者组 + 手动 ACK 的价值。消费者领走一条消息后，这条消息会同时进入这个消费者的 PEL（Pending Entries List）。只有调用 `XACK` 才会从 PEL 移除。如果消费者处理到一半崩溃了——没来得及 ACK——这条消息就一直留在它的 PEL 里。
>
> 我的恢复机制是一个 `@Scheduled(fixedRate = 30000)` 的定时任务，每 30 秒跑一次：
> 1. 先从 Redis 读上次的巡检游标（`short-link:stats-stream:recover-cursor`，初始 "0-0"）
> 2. 通过 Lua 脚本执行 `XAUTOCLAIM`，认领"空闲超过 2 分钟（minIdleMs）"的消息，每批最多 200 条
> 3. 把认领到的消息反序列化，调用 `consumer.onMessage(record)` 重新走一遍消费逻辑
> 4. 更新游标到 Redis，下一轮从这继续
>
> `XAUTOCLAIM` 是原子操作，它会同时把消息从原消费者的 PEL 转移到新消费者（`stats-recoverer`）名下，避免竞态。游标持久化在 Redis 而不是内存，保证应用重启后巡检进度不丢。

#### Q3：消费过程中抛异常了怎么办？消息会一直重试死循环吗？

> **A：** 分三种异常分别处理：
>
> **业务异常**（比如数据库连接超时）：catch 块里调用 `release(messageId)` 删除 Redis 幂等标记，然后 re-throw。因为没有 ACK，消息留在 PEL 里，等下一轮巡检任务重新认领重试。
>
> **DuplicateKeyException**（唯一索引冲突）：说明这条消息已经被别的消费者处理过了，幂等标记刚好过期才放进来。直接当成功处理，skip 掉，不 ACK 也不报错——巡检任务后续会发现它，检查幂等标记是 "1"，执行补偿 ACK。
>
> **ACK 本身失败**（网络抖动）：业务已经成功、标记已设 "1"，日志告警。下次巡检认领到这条消息，发现标记是 "1"，直接补偿 ACK。
>
> 理论上消息可以被无限次重试。为了避免真正的"毒消息"死循环，后续可以加最大重试次数限制——超过 5 次就写死信队列人工排查。当前因为有唯一索引兜底，即使无限重试也不会产生脏数据，只是浪费算力。

#### Q4：幂等标记 TTL 为什么是 2 分钟？完成标记为什么是 4 分钟？

> **A：** 这两个数字和巡检任务的 `minIdleMs` 是联动的。
>
> **2 分钟**对应巡检的空闲阈值。`XAUTOCLAIM` 认领的是"空闲超过 2 分钟"的消息。如果"处理中"标记（"0"）的 TTL 小于 2 分钟，会出现这种问题：消费者 A 还在正常处理，标记先过期了，巡检任务把消息认领给消费者 B，A 和 B 同时处理——并发消费。所以处理中标记的 TTL 必须 ≥ 2 分钟。
>
> **4 分钟**对应"已完成"标记（"1"）的保留时间。巡检任务认领消息后，会先检查标记：如果是 "1" 就直接补偿 ACK。这个 TTL 必须 > `minIdleMs(2min) + 巡检间隔(30s)` = 至少 2.5 分钟。设 4 分钟留了余量，保证巡检任务认领到这条消息时，"已完成"标记还在，能正确识别为"已处理"并补偿 ACK，而不会误当成新消息重新处理。

#### Q5：消费端一个事务里写多少张表？事务太大有问题吗？

> **A：** `LinkStatsSaver.save()` 在一个 `@Transactional` 事务里写访问日志、首访去重、地区、操作系统、浏览器、设备、网络、小时级汇总等 8 张表，外加更新 link 表的聚合计数器。
>
> 事务确实偏大，但在当前场景合理：这些写入是**单次访问产生的统计数据**，数据量可控（每次最多 8 条 INSERT + 几条 UPDATE），而且它们有**逻辑一致性要求**——PV 增量和 UV 增量必须同时成功，否则统计会对不上。如果拆成多个小事务，就要额外做补偿机制处理部分失败，复杂度反而更高。
>
> 如果未来统计维度继续增长，可以把维度统计拆到独立异步任务里，用最终一致性替代强一致性。或者把访问日志这种"流水"和维度统计这种"聚合"分开——流水先快速落库，聚合用定时任务批量计算。

#### Q6：Redis Stream 会不会内存溢出？怎么控制？

> **A：** Stream 会持续增长，必须主动控制。我用了一个 Lua 脚本 `stream_trim_minid.lua` 做修剪——通过 `XTRIM MINID` 保留最近的有效消息 ID，把已经被消费确认的旧消息删掉。也可以用 `MAXLEN` 限制 Stream 最大长度。
>
> 另外 PEL 里的消息虽然是"未确认"的，但它们的元数据也会占内存。这就是为什么巡检任务很重要——及时把超时消息重新处理掉并 ACK，让它们从 PEL 里清理出去，避免 PEL 无限膨胀。

## 二、分布式号段生成 — Redis INCRBY + 仿射置换 + Base62

### 📝 口述稿

> 短码生成是整个系统的核心，我的方案是**号段模式 + 仿射置换 + Base62 编码**三阶段流水线。
>
> **第一阶段：分布式号段分配。** 用 Redis 的 `INCRBY` 原子命令，一次取一整段号（默认 1 万个连续编号）。比如 Redis 计数器当前是 0，执行 `INCRBY 10000` 返回 10000，这个实例就拿到了 [1, 10000] 这一段。号段缓存在本地内存，之后每次生成短码，直接用 `AtomicLong.getAndIncrement()` 在本地自增取号，绝大多数生成请求无需访问 Redis。
>
> 当号段剩余量低于 20%（`PREFETCH_RATIO = 0.2`）时，用 `CompletableFuture.runAsync` **异步预取**下一段，存到 `AtomicReference<Segment>` 里。当前号段用完时：如果预取段已就绪，用 `getAndSet(null)` 无锁切换；如果预取还没完成，才走 `synchronized` 慢路径同步去 Redis 取。这样绝大多数请求完全无锁。
>
> **第二阶段：仿射置换。** 拿到线性序号 `i` 后，用公式 `y = (A·i + B) mod N`（N = 62^6 ≈ 568 亿）把它打散。参数 A 必须是奇数且与 62 互素，启动时严格校验。这是个**双射函数**——不同的 i 一定映射到不同的 y，所以短码绝对不会碰撞。同时让连续序号变得不可预测，用户看到 `Ab3xK9` 完全猜不出下一个短码是什么，防止恶意遍历。
>
> **第三阶段：Base62 定长编码。** 把 y 编码成恰好 6 位的 `[0-9A-Za-z]` 字符串，从末位向前填充，不够补 '0'，保证所有短码长度统一、美观。
>
> 跳转时不使用本地号段游标判断短码是否存在。多实例分别持有不同号段，本地游标无法代表其他实例的创建进度；错误地据此快速否定，会把其他实例创建的合法短码返回为 404。

### ❓ 面试官追问

#### Q1：为什么不用雪花算法（Snowflake）或 UUID？

> **A：** 几个方案各有取舍：
> - **UUID**：32 位十六进制，太长，完全违背"短"的初衷。
> - **雪花算法**：生成 64 位长整型（约 19 位十进制），Base62 编码后至少要 11 位字符才能放下，对短链接太长。而且雪花依赖机器时钟，要处理时钟回拨问题，复杂度高。
> - **我的方案**：号段 + 仿射 + Base62，6 位短码理论空间 62^6 ≈ 568 亿，够用 15 年；号段本地自增性能远超每次远程调用；仿射置换后短码不可预测；而且号段协调只靠 Redis INCRBY 一个原子命令，比雪花算法简单可靠得多。

#### Q2：仿射变换为什么能保证不碰撞？数学原理讲一下。

> **A：** 仿射变换 `y = (A·x + B) mod N` 是双射（一一映射）的**充要条件**是 `gcd(A, N) = 1`，即 A 与 N 互素。
>
> 在我的场景 N = 62^6，而 62 = 2 × 31，所以 N 的素因子只有 2 和 31。只要 A 既不是 2 的倍数（必须是奇数）、也不是 31 的倍数，就一定与 N 互素。代码里的校验就是这三条：`A % 2 != 0`（奇数）、`A % 31 != 0`、`gcd(A, 62) == 1`（冗余校验）。
>
> 因为是双射，不同的输入 x 一定映射到不同的输出 y。又因为序号 x 由 Redis INCRBY 保证全局唯一，所以最终短码也一定全局唯一，**数学上绝对不碰撞**，不需要像哈希方案那样处理冲突。
>
#### Q3：号段预取的并发安全性怎么保证？

> **A：** 用了几个原子变量配合，实现"无锁优先、有锁兜底"的混合方案：
>
> **快路径（无锁，99% 请求走这）：** `nextId()` 里 `cursor.getAndIncrement()` 拿到序号 c，如果 `c <= end`（在当前号段内），直接返回。同时调 `maybePrefetch()` 检查是否要触发预取——这里完全无锁。
>
> **预取触发：** `maybePrefetch()` 先看剩余量 `end - cursor + 1` 是否 ≤ `SEGMENT_STEP × 0.2`。是的话，用 `prefetching.compareAndSet(false, true)` 抢占预取权——只有一个线程能触发，避免重复预取。预取结果存到 `AtomicReference<Segment> nextSeg`。
>
> **号段切换（无锁优先）：** 当 `cursor > end`（号段用完），先尝试 `nextSeg.getAndSet(null)` 无锁取出预取段。取到了就 `switchTo` 切换，continue 重试。
>
> **慢路径（有锁）：** 预取段被别的线程取走了（返回 null），才进 `synchronized(LOCK)` 块。块内双重检查：先看游标是不是真的还在旧段外，再看预取段是不是刚好完成了，最后才同步去 Redis 拉新段。
>
> 整体效果：正常负载完全无锁，号段切换瞬间最多一个线程走慢路径。

#### Q4：Redis 挂了号段分配怎么办？

> **A：** Redis 不可用时，`fetchFromRedis()` 的 `INCRBY` 会抛异常，新号段取不到。**但当前号段如果还有剩余，分配完全不受影响**——因为号段已经缓存在本地内存了，自增不依赖 Redis。只有当号段耗尽且 Redis 仍不可用，`nextId()` 才会在 synchronized 块里反复失败。
>
> 系统的容灾能力取决于号段大小和 Redis 恢复时间。默认号段 1 万，假设创建 QPS 为 1000，一个完整号段理论上可继续分配约 10 秒。可以调大 `segmentStep` 增强短时容灾——代价是实例退出时可能浪费更多尚未使用的序号，但不影响唯一性。

#### Q5：6 位短码 568 亿空间够用吗？不够了怎么办？

> **A：** `62^6 = 56,800,235,584` ≈ 568 亿。按每天创建 1000 万个短链算，能用 5680 天 ≈ **15 年**。
>
> 真不够了有两个方案：一是把 `length` 从 6 调成 7，容量变 `62^7 ≈ 3.5 万亿`，代码里已经支持 6 和 7 两种长度（`ShortCodeProps.length`）；二是结合软删除做短码回收——过期的短码释放后重新分配，系统通过 `del_time` 软删除设计已经预留了这个能力。

#### Q6：为什么不能用反向解码结果和号段游标快速否定短码？

> **A：** 因为号段游标不是全局创建事实。实例 A 可能持有 `[1, 10000]`，实例 B 已持有并使用 `[10001, 20000]`；A 的本地游标小于 B 生成短码对应的序号，如果 A 据此否定，就会对合法短码返回错误 404。
>
> 直接读取 Redis 全局计数器也不可靠：号段在真正创建短链前就已整段分配，异步预取还会提前推进计数器，因此“序号已分配”不等于“短链已创建”。当前用 Bloom Filter 表示创建事实，用空值缓存吸收误判或已删除记录，最后由数据库做权威校验。

## 三、多级缓存防护 — Caffeine + Redis + 布隆过滤器 + 空值缓存 + 本地锁

### 📝 口述稿

> 跳转是系统流量最大的路径，QPS 可能是创建的几十倍，必须做到毫秒级响应。我设计了一套**四层缓存漏斗**做纵深防御，从最快到最慢逐层拦截。
>
> **第 1 层 · Caffeine 本地缓存。** 进程内访问，零网络开销。最多 10000 条，TTL 10 分钟。热点短链接直接命中，响应在微秒级。
>
> **第 2 层 · Redis 分布式缓存。** 多实例共享。Key 是 `short-link:goto:{fullShortUrl}`，TTL 跟随短链有效期——链接设了 1 天过期，缓存 TTL 就是 1 天；永久链接默认缓存 30 天。命中后回填 Caffeine，下次走本地。
>
> **第 3 层 · 存在性预判。** Redisson 布隆过滤器预期容量 1 亿、误判率 0.1%，用于否定“从未被创建过”的短码。这里不使用本地号段游标，避免多实例间创建进度不同导致误判。
>
> **第 4 层 · 空值缓存。** 确认不存在的短码，写一个 30 分钟 TTL 的负向标记。30 分钟内重复请求直接 404，不反复查库。防"缓存穿透"。
>
> **缓存击穿防护**——热点 key 过期瞬间大量并发请求打到 DB：我用 **本地 ReentrantLock + 双重检查**。锁按短地址粒度存在 Caffeine 锁池里。获取锁后在锁内再查一遍 Caffeine 和 Redis（双重检查），因为等锁期间别的线程可能已经回填了缓存。只有双重检查都 miss 才真正查 DB。
>
> **为什么用本地锁不用分布式锁？** 因为分布式锁每次要两趟 Redis 往返（加锁 + 解锁），高并发下会把尾延迟放大好几倍。本地锁是纯内存，快得多。代价是多实例可能各自查一次 DB——但 SELECT 是幂等的，多查一次无伤大雅。这是"用偶尔的重复查询换确定性的低延迟"的权衡。

### ❓ 面试官追问

#### Q1：为什么不用分布式锁（Redisson）？多实例不会有并发问题吗？

> **A：** 这是延迟和准确性的权衡。分布式锁能保证多实例间严格互斥，但每次加锁解锁至少两次 Redis 往返。在跳转这个对延迟极敏感的热路径上，如果大量请求同时 miss 缓存，分布式锁会成为瓶颈，尾延迟可能从 1ms 飙到几十 ms。
>
> 本地锁确实无法跨实例互斥——两个实例可能同时查 DB。但这不是问题，因为：
> 1. 数据库查询是**幂等**的（只是 SELECT），不会产生数据不一致；
> 2. 前面有布隆过滤器和空值缓存两道前置过滤，真正走到 DB 的请求已经很少了；
> 3. 即使偶尔两个实例同时查同一条记录，也就多一次 SELECT，远比分布式锁的延迟开销小。
>
> 设计哲学是：**用偶尔的重复查询，换确定性的低延迟**。在"读多写少 + 读幂等"的场景下，这个权衡是划算的。

#### Q2：空值缓存 TTL 为什么是 30 分钟？太长太短各有什么问题？

> **A：**
> - **太短（比如 1 分钟）**：攻击者高频请求不存在的短码，每分钟穿透一次到 DB，防不住。
> - **太长（比如 24 小时）**：如果短码被删除后又重新创建（系统支持软删除后重用短码），空值缓存会导致新创建的短链很长一段时间跳转 404。
>
> 30 分钟是平衡点：足以抵御短时高频穿透攻击，短码重用后最多 30 分钟恢复。而且创建短链时代码会主动清除该短码的空值缓存（`delete(GOTO_IS_NULL_SHORT_LINK_KEY)`），所以重用场景实际影响更小。

#### Q3：布隆过滤器误判了怎么办？

> **A：** 布隆过滤器的误判只可能是"假阳性"——说"可能存在"但实际不存在。误判时我们会继续走空值缓存检查和数据库查询，最终正确返回 404。**不会导致数据错误，只是多一次不必要的 Redis 查询。**
>
> 误判率配置为 0.1%，意味着 1000 次无效短码查询约有 1 次多打一次 Redis，完全可接受。
>
> 布隆过滤器**不会假阴性**（不会漏判）——只要元素被 add 过，contains 一定返回 true。这是它的数学性质决定的。所以"说没有就一定没有"这条是绝对可靠的，能放心用来否决。
>
> 补充：布隆过滤器**不支持删除**。如果短链被删了，过滤器里的标记还在。但这不影响正确性——删了的短链会走到空值缓存那一步被拦住。

#### Q4：缓存和数据库一致性怎么保证？

> **A：** 短链接本质是"写少读多"，一致性要求不高。代码做了针对性处理：
>
> 1. **创建时主动预热**：新建短链立即写 Redis 缓存 + 布隆过滤器，首个跳转请求就能命中。
> 2. **更新时主动失效**：修改 originUrl/validDate/validDateType 时，删除 Redis 缓存和 Caffeine 缓存。如果旧链已过期但新有效期在未来，还会清空值缓存。
> 3. **跨组移动（gid 变更）**：因为分片键变了，用分布式读写锁保护——先软删旧记录，再插新记录（新 gid 路由到不同分片），更新路由表，失效 GID 缓存。
>
> 由于短链创建后基本不改、有效期最长也就几天，一致性窗口非常小，对业务可忽略。

#### Q5：Caffeine 缓存满了怎么淘汰？

> **A：** Caffeine 用的是 **W-TinyLFU** 策略——结合了 LRU（最近最少使用）和 LFU（最不经常使用）的优点。它能有效识别真正的热点数据，避免 LRU 的"扫描污染"问题（一次全表扫描把热点全挤出去）。
>
> 配置了 `maximumSize(10000)` 和 `expireAfterWrite(10min)`。达到容量时淘汰最不常用的，10 分钟没访问的也会过期。还开了 `recordStats()` 监控命中率方便调优。
>
> 锁池 `redirectLockCache` 也是 Caffeine 管理的，按短地址存 ReentrantLock。某个 key 不再被访问，对应的锁对象会被自动淘汰释放内存。

#### Q6：跳转用 302 重定向而不是 301，为什么？

> **A：** 这是面试常考的一个细节。
> - **301（永久重定向）**：浏览器会**强缓存**，下次再点这个短链，浏览器直接用缓存的跳转地址，**根本不请求我们的服务器**。好处是省服务器压力，坏处是**统计不到后续点击**，而且如果短链的目标地址改了，用户看到的还是旧地址（缓存没过期）。
> - **302（临时重定向）**：浏览器**每次都请求服务器**。好处是每次点击都能统计到，目标地址改了立即生效；坏处是服务器压力大。
>
> 短链接系统的核心价值之一就是"统计追踪"，所以必须用 **302**，保证每次点击都能被记录。这也正是前面异步统计、多级缓存这些设计存在的意义——用它们来扛住 302 带来的高请求量。

## 四、双层接口限流 — Guava RateLimiter + Redis Lua 滑动窗口

### 📝 口述稿

> 限流是保护系统不被突发流量打垮的第一道防线。我做了**两层纵深防御**：
>
> **第一层 · 接口级限流**，基于 Guava `RateLimiter`（令牌桶算法）。在 Spring Filter 层（`@Order(HIGHEST_PRECEDENCE)`，最高优先级，认证之前就拦截）按接口分类配置：跳转限流器、创建限流器、统计限流器各自独立。限流开关关闭时，创建一个 `Double.MAX_VALUE` 的"无限令牌桶"作为 bypass。
>
> 令牌桶允许一定程度的突发——桶里攒了令牌就可以一次性消耗多个。批量创建接口消耗 5 个令牌（因为内部循环调用单条创建，一次 API 调用消耗 5 倍资源）。被限流的跳转请求返回一个**友好 HTML 429 页面**，带"立即重试"和"复制短链"按钮（因为跳转请求来自浏览器，返回 JSON 用户体验差）；API 请求返回 JSON 错误体。
>
> **第二层 · 用户级限流**，基于 Redis + Lua 脚本的滑动窗口。以用户名为 key（未登录用 PUBLIC_USERNAME），在时间窗口内统计请求次数，超过阈值拒绝。这层是**分布式**的，跨所有实例共享计数，防止单用户在集群维度绕过限制。
>
> 两层配合：Guava 挡掉大部分突发流量（单机），Redis 做精细化的用户维度控制（全局）。

### ❓ 面试官追问

#### Q1：为什么第一层用令牌桶而不是漏桶？

> **A：** 核心区别：令牌桶允许**突发**（桶里攒了令牌就能一次性消耗多个），漏桶强制**匀速**（不管积压多少，出水速度恒定）。
>
> 短链接场景下，用户访问天然不均匀——可能短时间内集中点几个热门链接，然后长时间空闲。令牌桶允许这种突发，体验更好。漏桶会强行削平所有流量，对合法用户不够友好。
>
> 另外 Guava RateLimiter 实现成熟、API 简洁（`tryAcquire(permits, timeout, unit)`），配合超时等待能平滑微突发——短暂等待而非直接拒绝。

#### Q2：Guava RateLimiter 是单机的，多实例部署总 QPS 会失控吗？

> **A：** 确实——每个 JVM 有自己的令牌桶，3 个实例各限 1000 QPS，集群总 QPS 能到 3000。但这个场景下**不是问题**：
>
> 1. 接口级限流的目的是**保护单个实例不被打挂**，只要每个实例有自己的限流就行；
> 2. 真正精细的全局限流由第二层 Redis 分布式限流承担；
> 3. 前面通常有 Nginx/Caddy 做负载均衡，流量大致均匀分配，`总流量/实例数 < 单机阈值` 就是安全的。
>
> 如果需要全局精确限流，可以改用 Redis + Lua 的分布式令牌桶，但会牺牲一些性能。当前双层设计已覆盖绝大多数场景。

#### Q3：用户级滑动窗口限流的 Lua 脚本具体做了什么？为什么必须用 Lua？

> **A：** 核心逻辑是滑动窗口计数（用 INCR + EXPIRE 组合）：
> 1. 以用户名为 key，执行 `INCR`，返回当前窗口内请求计数；
> 2. 如果返回值是 1（第一次请求），同时 `EXPIRE` 设置时间窗口（比如 5 秒）；
> 3. Java 侧比较返回值和配置阈值，超过返回 429。
>
> **必须用 Lua 的原因**：保证 INCR 和 EXPIRE 的**原子性**。如果分开执行，INCR 之后、EXPIRE 之前如果进程崩溃，这个 key 就永远没过期时间，用户被永久限流。Lua 脚本在 Redis 里是原子执行的，不会被打断。
>
> （更精确的滑动窗口可以用 Sorted Set + ZREMRANGEBYSCORE + ZCARD，但当前实现用 INCR 计数已满足需求，且更轻量。）

#### Q4：批量创建为什么消耗 5 个令牌而不是 1 个？

> **A：** 因为批量创建接口内部是**循环调用单条创建**——用户传 10 个 URL，实际产生 10 次数据库写入和 10 次短码生成。如果只消耗 1 个令牌，相当于用 1 次 API 调用消耗了 10 倍系统资源，这是个明显的**限流绕过漏洞**。
>
> 消耗 5 个令牌是折中——假设平均批量大小约 5，既能防滥用，又不过分限制正常批量操作。更精确的做法是根据请求体里 URL 数量动态消耗令牌，但那要在过滤器里解析请求体，增加复杂度。

#### Q5：被限流的跳转请求为什么返回 HTML 而不是 JSON？

> **A：** 因为跳转请求通常来自**浏览器**（用户点击短链），不是 API 客户端。如果返回 JSON，浏览器直接展示一堆 JSON 文本，用户体验极差。
>
> 返回一个简洁的 HTML 页面，告诉用户"访问太频繁"，并提供"立即重试"和"复制短链"按钮，用户点一下就能重试。这是面向用户的**降级策略**，体现的是工程上对用户体验的关注。
>
> 而 API 请求的调用方是程序，所以返回标准 JSON 错误体 `{"code":"B100000","message":"当前流量较高，请稍后再试..."}`，方便程序解析处理。代码里通过 `isRedirectPath()` 区分两种情况。

## 五、HyperLogLog 去重统计 — UV/UIP 内存优化

### 📝 口述稿

> 访问统计要算 PV、UV、UIP。PV 简单，点一次加一次。但 UV（独立访客）和 UIP（独立 IP）需要**去重**——同一个人点 100 次也只能算 1 个 UV。
>
> 传统方案是用 Redis Set 存每个访客标识，`SCARD` 取数量。但 Set 内存与成员数成正比——一个热门短链每天 10 万 UV，Set 要存 10 万个字符串，每个 20+ 字节就是 2MB，长期累积内存爆炸。
>
> 我用 **HyperLogLog** 替代 Set。它是概率数据结构，**固定 12KB 内存**就能统计 2^64 个元素的去重数，误差约 0.81%。`PFADD` 添加，`PFCOUNT` 取估算值，都是 O(1)。
>
> 但有个挑战：我不仅要知道总数，还要知道**每条访问带来的增量（delta）**——这样才能累加到数据库聚合计数器。所以写了个 Lua 脚本 `hll_count_add_delta.lua`，原子地完成：先 `PFCOUNT` 记旧值 → `PFADD` 加新元素 → 再 `PFCOUNT` 取新值 → 差值就是 delta。用 Lua 保证这三步原子，避免并发 PFADD 干扰 delta 计算。
>
> 另外，UV 需要按天重置。我用了个巧妙设计：HLL 的 key 里带 `epochDay % 2`（天数的奇偶）。奇数天用一组 key，偶数天用另一组，配合 24 小时 TTL 自动清理。只用两组 key 就实现日活自动重置，不用每天凌晨跑清理任务。查询今日数据时，按当前 `epochDay % 2` 去对应那组 key 查。

### ❓ 面试官追问

#### Q1：HyperLogLog 原理是什么？为什么只需 12KB？

> **A：** 核心是"概率计数"。它观察哈希值中的**前导零**个数来估算集合大小——直觉上：如果集合有 N 个唯一元素，哈希值中观察到的最大前导零数大约是 `log2(N)` 个。比如最大前导零是 10，集合大小约 `2^10 = 1024`。
>
> 为了提高精度，把哈希值分成 m 个桶。Redis 中 m = 16384，每个桶只记录该桶观察到的最大前导零数（6 bit 足够，因为最大值不超过 64）。16384 × 6 bit ≈ **12KB**，这就是固定开销的来源。
>
> 最终估算值用调和平均数公式计算并做偏差修正，精度 `1.04/√m` ≈ 0.81%。对 UV/UIP 这种统计数据完全够用。

#### Q2：Lua 脚本里的 delta 计算具体怎么做？为什么不能在 Java 里分步调？

> **A：** Lua 脚本逻辑：
> ```
> before = PFCOUNT(hll_key)
> PFADD(hll_key, element)
> after  = PFCOUNT(hll_key)
> delta  = after - before
> EXPIRE(hll_key, ttl)
> return delta
> ```
> **必须在 Lua 里原子执行**的原因：如果在 Java 里分三次调 Redis，PFCOUNT 和 PFADD 之间可能有**其他消费者的 PFADD 插进来**，导致 delta 计算不准——可能算成别人的增量，或者重复计算。Lua 脚本在 Redis 里是原子执行的，整个过程中间不会有别的命令插队。
>
> 数据库聚合表存的是 delta 增量，通过 `ON DUPLICATE KEY UPDATE uv = uv + delta` 累加。delta 是 0（老访客）UV 不变，delta 是 1（新访客）UV+1，和 HLL 去重语义对齐。

#### Q3：奇偶日轮转 key 设计具体怎么工作？

> **A：** 假设今天 6 月 15 日，`epochDay = 20254`，`20254 % 2 = 0`，今天的 UV key 是 `stats:uv:0:{shortUrl}`。
>
> 明天 6 月 16 日，`epochDay = 20255`，`20255 % 2 = 1`，key 变成 `stats:uv:1:{shortUrl}`。
>
> 后天 6 月 17 日，`20256 % 2 = 0`，又回到 `stats:uv:0:{shortUrl}`——但这时前天的 key 已经过期了（24 小时 TTL），所以相当于全新开始。
>
> **只用两组 key 就实现日活自动重置**，不需要每天凌晨跑定时任务清理，也不存在 key 爆炸问题。查询今日数据时按 `epochDay % 2` 找对应那组 key 就行。

#### Q4：0.81% 误差对业务有什么影响？

> **A：** 业务上完全可接受。数据分析关注的是**趋势和量级**，不是精确到个位数。比如报告显示 UV 10 万，实际在 99190~100810 之间，对运营决策没影响。
>
> 但有个细节要注意：HLL 的 delta 偶尔会是 0，即使加了一个新元素——因为 PFADD 后 PFCOUNT 的概率估算可能没变化。单次 delta 不准，但长期累积趋于准确，统计上可接受。
>
> 另外注意：HLL **不支持删除**。如果要剔除某个访客只能重建。但短链统计场景不需要删除，所以没问题。

#### Q5：用户清了 Cookie 或换了 IP，会被算成新 UV 吗？

> **A：** 会的。UV 标识来自 Cookie 里的会话标识（未登录）或用户 ID（登录后）。清了 Cookie 标识就变，会被算成新 UV。
>
> 这是业界通用做法。要精确识别"同一个人跨设备跨会话"，需要更复杂的用户画像体系（账号打通、设备指纹等），超出当前项目范围。对于短链的流量趋势分析，当前精度足够。

#### Q6：为什么 PV 不用 HyperLogLog？

> **A：** 因为 PV 是**简单加法**——点一次 +1，不需要去重。直接用 Redis `INCR` 就行，或者直接在数据库聚合表 `UPDATE pv = pv + 1`。
>
> UV/UIP 才需要去重（同一个人点 100 次算 1 个 UV），才需要 HyperLogLog 这种概率去重结构。如果 PV 也用 HLL，反而引入了不必要的 0.81% 误差——PV 本来可以做到精确。

## 六、MCP 工具接入 — 对 AI 智能体开放短链能力

### 📝 口述稿

> 随着 AI 智能体普及，我给系统加了一个 **MCP（Model Context Protocol）** 接口，让外部 AI 助手能直接调用短链创建能力。
>
> MCP 是 Anthropic 提出的开放协议，用于标准化 AI 模型和外部工具的交互。我用官方 Java SDK 实现，通过 **SSE（Server-Sent Events）** 传输协议暴露两个端点：SSE 端点 `/api/mcp` 建立长连接，消息端点 `/api/mcp/message` 接收工具调用，20 秒 keep-alive 心跳防超时。
>
> 注册了一个核心工具 `createShortLink`，参数用 JSON Schema 描述：`originUrl` 必填、`describe` 选填。AI 助手调用后，系统切到公共用户上下文（PUBLIC_USERNAME）创建一条 3 天有效短链，结果以结构化文本返回。
>
> 这样任何支持 MCP 的 AI 客户端（Claude Desktop 等）都能无缝接入，等于把短链能力变成 AI 生态里的一块"乐高积木"。

### ❓ 面试官追问

#### Q1：MCP 和普通 REST API 有什么区别？为什么要用 MCP？

> **A：** REST API 是给**程序员**用的——要读文档、写调用代码、处理鉴权。MCP 是给 **AI** 用的——AI 通过协议自动发现和理解工具，不用人工写集成代码。
>
> MCP 有三个核心概念：
> - **Tools**：服务端暴露的函数，有 JSON Schema 描述输入输出，AI 能理解工具用途和参数含义。
> - **Resources**：服务端提供的数据源（文件、DB 记录），AI 可读取丰富上下文。
> - **Prompts**：服务端提供的提示模板，帮 AI 更好用工具。
>
> 优势：标准化（不同 AI 框架都能接入）、即插即用（AI 自动发现工具）、类型安全（Schema 约束参数）。对人类用户仍保留 REST API，MCP 主要面向 AI 场景。

#### Q2：SSE 传输和 HTTP 传输有什么区别？为什么选 SSE？

> **A：** MCP 支持两种传输：
> - **Stdio**：通过标准输入输出通信，适用于本地进程间（MCP Server 跑在 AI 客户端同机器上）。
> - **SSE + HTTP**：SSE 用于服务端→客户端推送（工具列表变更、keep-alive），HTTP POST 用于客户端→服务端（工具调用）。适用于远程部署。
>
> 我选 SSE + HTTP，因为短链服务是 Web 应用部署在服务器上，AI 客户端通过网络远程连接。SSE 端点保持长连接，20 秒发一次心跳防超时断开，HTTP 消息端点处理实际调用，30 秒超时。

#### Q3：工具调用为什么要设置 PUBLIC_USERNAME 上下文？

> **A：** 因为 MCP 工具调用**不经过认证过滤器**（不携带 Bearer Token），所以 `UserContext`（基于 ThreadLocal 的用户上下文）是空的。不手动设置的话，`createLink()` 会因为找不到当前用户报错。
>
> 设置为 PUBLIC_USERNAME，意味着 MCP 创建的短链归公共用户、强制放入 PUBLIC_GID 默认分组——和未登录用户在网页上创建的行为一致。
>
> 工具调用完成后，通过 `finally` 块清理 UserContext，**避免线程复用时上下文泄漏**（这是 ThreadLocal 的经典坑）。

#### Q4：如果要给 MCP 加更多工具（查统计、删短链），架构怎么调整？

> **A：** 当前是在 `ShortLinkMcpServer` 的 `@Bean` 里通过 `McpServer.sync(provider).toolCall(...)` 注册工具。加工具只需多调几次 `.toolCall()`，每个定义自己的 Schema 和处理函数。
>
> 更好的做法是抽成**注解驱动**：自定义 `@McpTool` 注解，扫描标注方法自动注册，像加 Controller 接口一样简单。
>
> 对需要认证的工具（查某用户统计），可以在 MCP 层实现 OAuth 2.0，或通过 API Key 让客户端携带凭证。

#### Q5：MCP 有什么实际使用场景？

> **A：** 最直接：用户对 AI 说"帮我把这个链接缩短"，AI 识别意图自动调 `createShortLink`，返回短链。比打开网页手动创建更方便。
>
> 进阶场景：扩展查询统计工具后，用户问"我上周的短链有多少点击"，AI 调统计工具生成报告；或在自动化营销工作流里，AI Agent 生成内容时自动创建带追踪的短链。本质是让短链能力进入 AI 自动化的链条里。

## 七、AI 运营助手（AI Copilot）— ReAct Agent 智能分析

### 📝 简历要点

> 基于 AgentScope Java 2.0 构建 ReAct Agent 智能分析助手，设计 6 个领域工具（流量统计、链接对比、异常检测、健康检查等），通过 SSE 流式协议实现前后端实时交互，支持多轮对话上下文与会话持久化，为运营人员提供自然语言驱动的短链数据分析能力。

### ❓ 面试官追问

#### Q1：为什么要做 AI 运营助手？解决什么业务问题？

> **A：** 短链系统积累了大量访问数据（PV/UV、地区、设备、浏览器等维度），但运营人员要看数据必须手动进后台、选分组、选时间、翻图表，效率很低。特别是需要跨链接对比、找异常、查僵尸链接时，操作步骤更多。
>
> AI 运营助手的价值是让运营人员**用自然语言直接提问**——"本周流量怎么样"、"有没有异常"、"哪条链接表现最好"——Agent 自动选择工具、查询数据、生成分析报告，把"找数据"变成"问数据"。

#### Q2：ReAct Agent 是什么？为什么不直接调 API？

> **A：** ReAct 是 Reasoning + Acting 的缩写，Agent 不是简单转发请求，而是走一个**推理-行动-观察**的循环：
>
> 1. **Reasoning**：分析用户意图，比如"有没有异常流量"→ 需要检测异常
> 2. **Acting**：选择合适的工具调用，比如 `detect_anomalies` 工具
> 3. **Observation**：拿到工具返回的原始数据
> 4. **再 Reasoning**：基于数据生成可读的分析报告和优化建议
>
> 如果直接调 API，用户必须知道该调哪个接口、传什么参数。ReAct Agent 相当于加了一层"智能决策层"，理解模糊意图、自动选工具、组合多步查询。比如用户说"分析默认分组"，Agent 可能先调 `list_groups` 找到分组 ID，再调 `get_group_stats` 获取统计数据，最后生成报告——这是两次工具调用的链式推理。

#### Q3：6 个工具是怎么设计的？工具粒度怎么定的？

> **A：** 工具设计遵循"**一个工具解决一类问题**"的原则，分两层：
>
> - **StatsTools**（统计查询层）：`list_groups`（分组列表）、`get_group_stats`（分组级聚合统计）、`compare_links`（分组内链接排名对比）、`get_link_stats`（单条链接多维详情）
> - **InsightTools**（洞察分析层）：`detect_anomalies`（PV 骤降>50%、UV 飙升>100%、连续零流量检测）、`get_link_health`（过期/禁用/僵尸链接诊断）
>
> 粒度上，工具参数尽量简单（gid + 日期范围），复杂的数据聚合在工具内部完成。Agent 不需要知道底层是 JOIN 了哪张统计表、走了什么分片——工具封装了领域知识，Agent 只需要选对工具。

#### Q4：SSE 流式传输是怎么实现的？为什么不用 WebSocket？

> **A：** 后端用 Spring 的 `SseEmitter` 实现 Server-Sent Events。Controller 返回 `SseEmitter`，Agent 的响应式流（Reactive Stream）每产生一段文字就 `emitter.send()` 推送一个事件。定义了 5 种事件类型：`session_id`、`text`（文字增量）、`tool_call`（工具调用中）、`done`（完成）、`error`（异常）。
>
> 前端没有用浏览器原生 `EventSource`，因为它不支持自定义 Header（无法传 Authorization Token），也不支持取消请求。我手动用 `fetch + ReadableStream` 解析 SSE 协议，逐行读取 `event:` 和 `data:` 字段，实现了完整的 SSE 解析器，支持多行 `data:` 拼接、AbortController 取消。
>
> 选 SSE 而非 WebSocket 是因为 AI 对话是**单向流**（服务器→客户端），SSE 天然适合，协议更简单，基于 HTTP 无需额外端口，Spring 原生支持。

#### Q5：多轮对话上下文怎么做的？上下文窗口怎么控制？

> **A：** 会话和消息持久化到两张 MySQL 表（`t_ai_session` + `t_ai_message`），每次发消息前加载该会话**最近 20 条消息**，按角色（user/assistant）转换成 AgentScope 的 `Msg` 列表传给 Agent，Agent 就有了历史上下文。
>
> 控制上下文窗口是 20 条（约 10 轮对话），原因：(1) 模型有 Token 上限，历史太长会截断或报错；(2) 运营分析场景通常只关心最近几轮的追问；(3) 减少 Token 消耗降低成本。
>
> 会话 ID 由前端用 `crypto.randomUUID()` 生成，首次发消息时后端幂等创建会话记录，首条消息自动截取前 30 字作为会话标题（类似 ChatGPT）。

#### Q6：异步线程里 UserContext 丢失是怎么解决的？

> **A：** 这是个经典问题。用户登录信息存在 `ThreadLocal`（实际是 TransmittableThreadLocal），但 Agent 的响应式流在独立线程执行，ThreadLocal 传不过去，`UserContext.getUsername()` 会返回 null。
>
> 解决方案很简单但关键：在 subscribe 回调**之前**（还在 HTTP 请求线程时），把 `username` 捕获到局部变量 `String username = UserContext.getUsername()`，然后在回调里用这个局部变量，而不是再次调用 `UserContext.getUsername()`。这是典型的"提前捕获上下文"模式。

## 八、整体架构与综合问题

### ❓ 面试官追问

#### Q1：这个系统的瓶颈在哪？日活从 10 万涨到 1000 万怎么扩展？

> **A：** 当前瓶颈：
> 1. **数据库写入**：统计异步入库缓解了瞬时压力，但批量入库仍是串行瓶颈；
> 2. **Redis 单点**：缓存、号段、限流都依赖单一 Redis；
> 3. **短码空间**：6 位 568 亿长期可能不够（虽然够用 15 年）。
>
> 扩展方案：
> 1. **数据库**：统计表按 `full_short_url` 分片；引入 ClickHouse/Doris 做 OLAP 分析；
> 2. **Redis**：Redis Cluster 或 Sentinel 高可用；号段分配用 Slot 机制分散热点；
> 3. **短码**：动态调 length 到 7 位，或按用户隔离短码空间；
> 4. **缓存**：引入 CDN 边缘缓存，跳转请求在边缘节点消化。

#### Q2：ShardingSphere 怎么用的？为什么按 gid 分片？

> **A：** 按 `gid`（分组 ID）哈希分 16 张表（`t_link_0` ~ `t_link_15`）。路由表 `t_link_goto` 按 `full_short_url` 分片——这样跳转时凭短地址就能一次查到 gid，再去对应分片查详情。
>
> 按 gid 分片的理由：
> 1. **同组数据局部性**：用户通常批量操作同一组的链接，同组数据落同一张表，减少跨片查询；
> 2. **负载均衡**：16 分片均匀分布，避免单表倾斜；
> 3. **水平扩展**：未来加分片数不影响现有数据。

#### Q3：项目里用了哪些设计模式？

> **A：**
> - **策略模式**：IP 地理位置查询支持多实现（本地 ip2region、高德 API），通过 `IpGeoClient` 接口抽象，配置切换。
> - **生产者-消费者**：Redis Stream 的 Producer/Consumer，解耦跳转和统计入库。
> - **责任链**：Servlet Filter 链——RateLimitFilter → UserFlowRiskControlFilter → UserTransmitFilter/ApiTokenAuthFilter，按优先级依次处理。
> - **模板方法**：MyBatis Plus 的 `ServiceImpl<Mapper, Entity>` 提供 CRUD 模板。
> - **双检锁（DCL）**：跳转的缓存未命中处理——先无锁查缓存，miss 后加锁，再 double-check。

#### Q4：印象最深的技术难点是什么？

> **A：** **多级缓存与多实例正确性的权衡**。普通缓存方案（本地 + Redis）很多项目都有，但这个项目重点处理了三个边界：
> 1. Bloom Filter + 空值缓存分层拦截无效请求，降低数据库回源；
> 2. 缓存击穿用**按短链隔离的本地锁 + 双重检查**，避免在跳转热路径引入分布式锁网络往返；
> 3. 主动移除了基于本地号段游标的错误快速否定，避免多实例各持不同号段时误伤合法短码。
>
> 这套设计优先保证多实例正确性，再通过分层缓存降低跳转延迟；具体吞吐应以明确环境下的压测结果为准。

#### Q5：项目还能怎么优化？

> **A：**
> - **批量创建并行化**：当前是串行循环，可用 `CompletableFuture.supplyAsync + allOf` 并行，配合线程池控制并发度；
> - **分布式限流**：Guava 是进程级，多实例总 QPS 会放大，可引入 Redis 分布式令牌桶或 Sentinel；
> - **统计表分片**：访问日志和六维统计表未分片，数据量大了会成瓶颈，按 `full_short_url` 或时间分片；
> - **统计结果缓存**：统计查询直接查 DB，可加 Redis 缓存（TTL 5 分钟）降 DB 压力。

#### Q6：为什么 302 而不是 301？为什么跳转和统计要解耦？

> **A：** 301 会被浏览器强缓存，后续点击不请求服务器——**统计不到**，而且目标地址改了不立即生效。302 每次都请求服务器，保证每次点击可统计、改地址立即生效。短链核心价值就是追踪，所以必须 302。
>
> 解耦是因为统计是"重操作"（要解析 UA、查 IP 归属、写多张表），如果在跳转热路径同步做，响应时间从毫秒级飙到几十甚至上百毫秒，高并发下还会打满 DB 连接池。用 Redis Stream 异步化后，跳转只多一次 XADD（微秒级），用户体验无感知，统计在后台慢慢落盘。这是典型的"用最终一致性换实时性能"。

## 附：高频通用问题速查

| 问题 | 一句话答案 |
|------|-----------|
| 为什么 at-least-once 而不是 exactly-once？ | exactly-once 实现极复杂（需两阶段提交/事务消息），at-least-once + 幂等消费在工程上性价比最高 |
| Redis 挂了整个系统还能用吗？ | 跳转能扛一段时间（本地 Caffeine + 号段剩余），但创建新短链、统计、分布式限流会受影响 |
| 为什么不直接用 Spring Cache 抽象？ | Spring Cache 抽象不够灵活，多级缓存、空值缓存、本地锁这些精细控制需要手写 |
| BCrypt 和 AES 分别用在哪？ | 密码用 BCrypt（不可逆+加盐防彩虹表）；手机号邮箱用 AES（需要反查明文，对称加密） |
| ThreadLocal 用在哪？有什么坑？ | 用户上下文 UserContext 用 ThreadLocal；坑是线程池复用会上下文泄漏，必须在 finally 清理 |
| 怎么保证短码不重复？ | 数学保证：号段全局唯一（Redis INCRBY）+ 仿射双射（不同输入不同输出），不需要查重 |
